# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm start        # Static preview of the public site at http://localhost:8080 (python3 -m http.server)
npm run admin    # Local CMS (Express) at http://localhost:3030/admin, also serves /images and /tools/admin at :3030
npm run build    # Image pipeline + regenerates data/galleries.json (scripts/build.js)
npm test         # Runs test/*.test.js with node --test
```

`start-cms.command` is a macOS double-click wrapper around `npm run admin`.

There are 17+ tests under `test/`, run with `npm test`.
They cover the CommonJS helpers in `scripts/lib/` (`safe-path.js`, `variants.js`, `image-sizes.js`), not the browser-loaded ES modules or the Express routes themselves.
Beyond that, verification of the public site and the CMS is manual: run the site and look at it.
`scratch/puppeteer-test.js` is an ad-hoc screenshot script and puppeteer is **not** a declared dependency, so install it on demand if you want automated screenshots.

## Architecture

Vanilla static site: two HTML pages, native ES modules, no framework and no build step for JS/CSS.
`scripts/main.js` is the only entry point for both pages and acts as the router: it sniffs `window.location.pathname` for `gallery.html` and calls `initGalleryPage()`, otherwise `initHomePage()`.
Everything else is an `init*` function exported from a single-purpose module (`theme.js`, `ui.js`, `home.js`, `gallery.js`, `lightbox.js`), plus two small shared helper modules: `images.js` (responsive `src`/`srcset` attribute building) and `dom.js` (`esc()`, see below).

`styles/main.css` contains only `@import` statements; the cascade order there (variables → reset → layout → components → lightbox → utilities) is load-bearing, so add new modules in the right slot rather than appending.
Design tokens live in `styles/variables.css` under `:root` and are redefined under `[data-theme="dark"]`.

### Data flow (the important part)

Four JSON files under `data/`, with different roles:

- `data/favourites.json` is **hand/CMS-edited source of truth** for the Favourites collection. Entries are either a plain string or `{ "src": "gallery-id/file.webp", "featured": true }`. All consumers must handle both shapes.
- `data/gallery-meta.json` is **hand/CMS-edited source of truth** for per-gallery presentation metadata: the array order is the presentation order on the home within each category section, and each entry carries `category` (`photography` or `in-game`), an optional `platform` (`ps4`, `ps5`, `switch`, `switch-2`), and an optional `description` override. A folder present in `images/` but absent from this file falls back to `in-game`, no console, sorted last alphabetically. `favourites` must never appear here and is rejected in validation. Parsed and validated by `scripts/lib/gallery-meta.js` (`validateMeta`, `indexMeta`, `resolveMeta`, `sortGalleries`).
- `data/galleries.json` is **generated output** of `scripts/build.js` (and rewritten by the CMS's `/api/save`) and is what the browser actually fetches. Build scans `images/*/`, resolves each folder against `gallery-meta.json`, sorts by the meta order, then prepends a synthetic gallery with `id: "favourites"` built from `favourites.json`. A gallery object carries `platform` only when the meta defines one.
- `data/image-sizes.json` maps a gallery-relative path (`"japan/japan-13.webp"`) to its `{ w, h }` intrinsic dimensions. It is generated by `scripts/build.js` (via `scripts/lib/image-sizes.js`) and consumed by `scripts/images.js` on the browser side to emit `width`/`height`/`srcset` attributes without a network round trip.

Path conventions differ per field and are easy to get wrong:

- A normal gallery's `images[]` holds **bare filenames**, resolved at render time as `images/<gallery.id>/<file>`.
- The favourites gallery's `images[]` holds **gallery-relative paths** (`japan/japan-13.webp`), resolved as `images/<src>`.
- `coverImage` always holds a **full path already prefixed with `images/`**.

`build.js` is stateful and partly destructive.
It reads the existing `galleries.json` to preserve manual image ordering and a still-valid `coverImage`, converts JPEG/PNG to 1920px-wide WebP via `sharp`, and **moves the originals into the gitignored `originals/` directory**.
It also writes two 640px/1280px responsive variants per image (`scripts/lib/variants.js`) alongside the 1920px original, and updates `data/image-sizes.json`.
Everything else in a gallery object is derived, so hand edits to `galleries.json` are overwritten on the next build: `title` comes from `formatTitle(folderName)`, and `description`, `category` and `platform` come from `data/gallery-meta.json` (resolved via `resolveMeta`).
A folder absent from the meta falls back to `in-game` with no console and lands at the end of the order, so **a new real-world photography gallery needs an entry in `gallery-meta.json`** with `"category": "photography"`, either hand-written or set from the CMS.
`build.js` also reorders `galleries` with `sortGalleries` before writing, which is what makes the CMS drag-and-drop order survive a build.

### Escaping convention

`data/galleries.json` and `data/favourites.json` are **untrusted input**, not trusted config: they can come from `POST /api/save` on the CMS, and even though that endpoint validates *shape* (ids, paths), it does not and should not constrain free-text fields like `title` or `description`.
Every template literal that interpolates a value from those files and assigns the result via `innerHTML` must pass that value through `esc()` from `scripts/dom.js` first.
This applies uniformly, including to values that look structural rather than free-text, such as a gallery `id` used inside an `href`.

### CMS (`admin-server.js` + `tools/admin/`)

Express server on port 3030 that serves only `/images` (static files, so the CMS can preview real images) and `/tools/admin` (the admin frontend), and mounts the admin UI at `/admin`.
It does **not** serve the repository root: that would expose `.git`, `node_modules`, and the data JSON files over HTTP.
All JSON mutations go through a serialized `AsyncQueue` (`dbQueue.enqueue`) to avoid interleaved read-modify-write corruption of the data files; new mutating endpoints must use it too.
`/api/save` accepts `galleries`, `favourites` and `meta` (any subset) and validates the full shape of each present block before writing anything (arrays, `safeSegment`-valid gallery ids, and either `safeFilename`-valid bare filenames or `safeSegment`/`safeFilename`-valid `gallery/file` paths depending on context; `meta` via `validateMeta`) and rejects the whole request on the first problem rather than writing a partial result.
`GET /api/data` returns `meta` alongside `galleries`, `favourites` and `availableFolders`.
The sidebar drag-and-drop now persists the presentation order into `gallery-meta.json` (via `syncMetaOrder` in `admin.js`), and the header carries a console `<select>` shown only for in-game galleries.
`/api/build` shells out to `npm run build`.
Uploads land in `images/<galleryId>/` via multer; uploading directly to `favourites` is rejected by design because favourites are references, not files.
Upload filenames are **normalized, not rejected**: `normalizeUploadFilename` in `scripts/lib/safe-path.js` transliterates accents, lowercases, and collapses unsafe characters into hyphens, so real-world names like PlayStation share captures (`"Ghost of Tsushima_20240115181523.jpg"`) are accepted instead of failing the whole batch.
Its output always passes `safeFilename` by construction.
Collisions within a batch or against files already on disk are disambiguated (`photo.jpg`, `photo-2.jpg`, ...).
`safeFilename` itself is unchanged and is still the right tool for endpoints that reference a filename that must already exist on disk (`/api/photo/delete`, `/api/photo/toggle-favourite`, `/api/gallery/set-cover`): there, rejecting instead of normalizing is correct.
The admin frontend is plain globals + inline `onclick` handlers with SortableJS from a CDN, deliberately unmodularised.

## Things that break silently

- **Deleting an image must clean up three places**: the file on disk, the owning gallery's `images[]`, and any `favourites.json` reference. `/api/photo/delete` does this; keep it that way.
- Scroll-driven reveal animations only run when `initScrollAnimations` adds `scroll-animations-enabled` to `<html>`, which it skips under `prefers-reduced-motion`. The favourites carousel and theme icon animation respect the same query.
- The header auto-hide uses a shared `isNavigating` flag in `ui.js`; programmatic smooth scrolling must set it, or the header hides mid-navigation.
- The console vocabulary is **deliberately duplicated** between `scripts/lib/gallery-meta.js` (`PLATFORMS`, CommonJS, for `build.js` and `admin-server.js`) and `scripts/platforms.js` (`PLATFORM_ORDER`/`PLATFORM_LABELS`, ES module, for the browser), because there is no bundler crossing that CJS/ESM boundary. Adding or renaming a console means editing both files.

## Conventions

- Public-site copy and code identifiers are in English; the CMS UI, project docs, and commit messages are in Spanish.
- Dynamic UI is built with template literals assigned via `innerHTML`; component classes follow simplified BEM (`gallery-card__title`). See "Escaping convention" above: anything interpolated from `data/*.json` goes through `esc()`.
- Third-party runtime dependencies are deliberately avoided on the public site. `sharp`, `express`, and `multer` are build/CMS-only.
